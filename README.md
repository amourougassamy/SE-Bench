# SE-Bench

**End-to-end structural engineering workflows for AI agents using standard engineering tools and human steering.**

SE-Bench evaluates whether an agent can maintain an engineering objective across
drawing interpretation, model edits, solver calls, result interpretation, human
revisions, and coordinated deliverables.

The intended unit of evaluation is an engineering work package. Three pillars
guide the project:

1. **Goal persistence and coordination:** preserve constraints and propagate
   changes through models, analysis, drawings, and reports.
2. **Precise tool use:** choose operations with valid engineering semantics,
   inspect results, and recover from failures.
3. **Engineering interpretation:** recognize usable results, governing behavior,
   unmet criteria, and limits on the conclusions supported by the analysis.

## Current status

This is the **first development scaffold**, not a published, validated benchmark.
It includes one small revision workflow, a real OpenSeesPy adapter, a tool host,
auditable state and results, a deterministic evaluator, and a scripted reference
client. The reference client performs 15 calls; it is a smoke test for the
infrastructure, not evidence of long-horizon AI ability. No language model has
been evaluated yet.

The drawing tool produces a dimensioned SVG schematic. The fixture also supplies
geometry as text/JSON, so **visual comprehension is not measured yet**. The
reference numerical results were generated by the pinned solver; independent
expert verification and human review of engineering explanations are pending.

## Quick start

Python 3.10+ is required. The tested environment is Linux with Python 3.12 and
OpenSeesPy/OpenSeesPyLinux 3.7.1.2. Native OpenSees availability on other platforms
depends on its wheels; a Linux environment is the reproducible starting point.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[solver]'
python -m se_bench list
python -m se_bench demo --workspace runs/demo-001
```

On Windows, activate with `.venv\Scripts\activate`; a Linux environment such as
WSL can be used for the tested solver configuration. There is no credential or
paid API requirement for the demo.

Use a new output directory for each attempt. Existing workspaces are never
overwritten. The demo prints `automated_success: true` after all automatic gates
pass. `research_success` remains `null` until the missing human validation and
study controls are implemented.

Inspect these generated files:

| File | Purpose |
| --- | --- |
| `model.json` | Final revision of the analysis model |
| `results/run-*.json` | Solver versions, input hashes, displacements, reactions, element forces, warnings |
| `drawing.svg` | Final frame schematic with revision and model hash |
| `report.json`, `report.md` | Structured and readable assessment |
| `.evaluator/trace.jsonl` | Ordered tool requests/responses, errors, timings, and hash chain |
| `.evaluator/grade.json` | Demo's automatic evaluation and remaining human-review status |

## First task: portal-frame revision

1. Inspect a supplied 6 m span, 4 m high portal frame.
2. Validate and analyze the baseline, inspect results, and produce a schematic.
3. Request a scripted engineering review.
4. Apply the instructed 8 m span and revised beam line load, retaining sections,
   support conditions, height, lateral load, and the displacement criterion.
5. Reanalyze, interpret the results, update the schematic/report, and submit.

The maximum absolute roof horizontal-displacement limit is **4.5 mm**, a supplied
task criterion, not a building-code limit. The pinned reference results are
approximately **4.455 mm** initially and **4.805 mm** after revision. Correctly
reporting the revised criterion failure is successful task behavior. No strength,
stability, connection, or code-compliance conclusion is established.

## Connect an agent

The runner exposes a provider-neutral JSON-lines tool protocol; agent planning
and any vision-agent delegation remain outside the benchmark host.

```bash
python -m se_bench init --workspace runs/agent-001 --agent-id my-agent-v1
python -m se_bench serve --workspace runs/agent-001
```

Send one JSON object per line on stdin; receive one response per line on stdout:

```json
{"tool":"tools.list","arguments":{}}
{"tool":"task.read","arguments":{}}
{"tool":"model.get","arguments":{}}
{"tool":"model.validate","arguments":{}}
{"tool":"solver.run","arguments":{}}
```

Inspect the solver response and use its actual `run_id` with `results.get`.
`tools.list` exposes nested JSON Schemas and descriptions for all ten task tools.
The agent chooses a valid sequence. `call --workspace ...` also accepts one
request from stdin, allowing separate processes to resume a workspace.

An evaluator can subsequently run:

```bash
python -m se_bench grade --workspace runs/agent-001
```

The tool host is **not** an MCP server or a provider-specific AI agent. Those are
future adapters. Tool names containing dots may need a reversible alias when
mapping to a provider's native function-name restrictions.

## Evaluation boundaries

- A model edit invalidates active validation, analysis, drawing, and report.
- Results and deliverables carry model hashes and revision metadata.
- Baseline review and final submission are enforced lifecycle checkpoints.
- The evaluator checks numerical outputs, equilibrium, preserved constraints,
  revision propagation, assessment correctness, and artifact consistency.
- Incorrect conclusions can be submitted but fail the evaluator: making valid
  API calls is insufficient for automatic success.
- Diagnostic check fractions explain failures; they are not the primary success
  metric. Explanation quality still requires human review.
- The public oracle and evaluator must be isolated from agents before held-out
  experiments. The current host is for trusted development, **not a security
  boundary**; filesystem hash chains detect accidental changes, not an adversary
  able to rewrite evaluator files.

## Tests

```bash
python -m unittest discover -s tests -v
```

Without the solver extra, pure-contract/runtime tests run and solver-dependent
tests explicitly skip. CI installs the solver extra and exercises the complete
workflow. The solver adapter is also checked against closed-form cantilever
solutions, including uniform loads and rotated local axes. This does not replace
independent verification of the portal reference model.
